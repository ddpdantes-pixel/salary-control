# Приёмка 64: удаление Apple Health через OTA

Дата: 16 октября 2026. Основа: `1933947c831bc05c6c1433ad4a318ec46067bf1e`.
Ветка: `feat/android-ota-64`. Это продолжение 64, не задача 65.
Статус: **BLOCKED — причина первого bootstrap/ready timeout не установлена**.
Candidate `.2` прошёл перечисленные ниже проверки, но это не доказывает исправления
сбоя `.1`. Stable-приёмка заблокирована; новые загрузки в QA приостановлены.
Samsung-приёмка и разрешение stable rollout не заявляются.
Пользователь сообщил об успешной установке APK 1.1.0 (3) поверх 1.0.0 на Samsung;
это пользовательское подтверждение, не новая автоматизированная проверка телефона.

## Аудит и границы

Удалены активные frontend-механизмы Apple Health: запуск/возврат iOS Shortcut,
fragment v1/v2 import, Worker fetch/POST/polling, focus/visibility sync, события
синхронизации, статусные notices, настройки, кнопки, ссылки и их CSS.
Общих зависимостей, используемых только этим кодом, не найдено. `package.json` и
lockfile не менялись; QR/clipboard/shared utilities используются другими функциями.
Старые инструкции Apple Health в документах прошлых задач не удаляются как история.

`appleHealthWater.ts` оставлен как небольшой совместимый модуль: четыре прежние
чистые функции расчёта воды и прежнее явное переключение записи на ручной ввод.
Импорта, сети, обработчиков URL и синхронизации в нём больше нет. Старые имена
полей/типов и нормализаторы в storage/settings сохранены без изменений. Поэтому
исторические миллилитры читаются без округления до кружек, записи не мигрируют.
В UI старая запись обозначена «сохранённая запись», а не Apple Health.
Выбор капли/«Сбросить» — явное редактирование только выбранного дня; используется
прежний helper ручного режима. Простое открытие не меняет исторический объём.

Backup, cloud contract, health export, вечерний чек-лист и канонический регламент
не менялись. В историческом текстовом экспорте сохраняется прежняя пометка источника
`(Apple Health)` ради точного контракта, но активной интеграции за ней больше нет.
Существующее исключение импортированной воды/секретов из backup также не менялось;
новой гарантии переноса таких legacy-полей через backup эта задача не добавляет.
Worker/D1 и прежние backend endpoints не удалялись и не модифицировались.

## Фактическая OTA-приёмка и замечание

На signed AVD `moyritm64-release` оставлена прежняя release APK 1.1.0 (3),
lastUpdateTime **2026-10-16 15:46:29 UTC**. При этой проверке APK не устанавливалась.
До OTA были видны Apple Health и версия `.7`; экспортирован свежий синтетический
backup (зарплата, финансы, два дня здоровья, обучение, цель с изображением).

Первая попытка `.1` действительно не прошла: HTTPS загрузка и криптография успешны,
но после первого cold start offline не пришёл notifyAppReady. Native log:
16:54:13.404 UTC set → 16:54:43.411 rollback (**30.007 s**) → рабочая `.7`.
Версия `.1` помечена error и не используется как финальный candidate. Причина этого
единичного timeout не установлена; он не объявляется исправленной ошибкой и не
выдаётся за успешный тест. Пакет не перезаписывался, проверки не отключались.

Для повторной проверки создан новый immutable `.2` с теми же web-файлами, другой
версией/ZIP metadata/подписью. Подтверждена реальная HTTPS загрузка; следующий cold
start при доступной сети активировал `.2`: 17:05:51.535 UTC Version successfully loaded,
затем реальный notifyAppReady. UI показал новую версию, Apple Health исчез.
Новая APK между загрузкой и запуском не устанавливалась.

Финальное сравнение всех 24 web-файлов `.1` и `.2` по пути и SHA-256 не нашло
различий. Исправлений исходного bootstrap-кода между пакетами не было. Таким
образом, таймаут `.1` не считается устранённым в `.2`: успешные повторы показывают
работоспособность и невоспроизводимость сбоя в этих прогонах, но не его причину.

- Backup до/после OTA: все поля, кроме createdAt нового файла, идентичны; goalImages тоже.
- Последующий полный cold start **offline**, Active default network=none: `.2` работает,
  Apple Health отсутствует; новый export снова совпадает с исходным.
- То же тестовое облачное подключение сохранилось. Restore прежней копии прошёл
  без нового подключения; последующий export опять идентичен исходному.
- Независимый signed AVD `moyritm64-stable`: после подготовки существующей QA APK
  выполнен первый запуск новых web assets `.2` сразу offline, без их предварительного
  запуска онлайн. Native set: **17:15:48.834 UTC**, ready: **17:15:52.160 UTC**,
  то есть **3.326 s**. Apple Health отсутствует, сеть отсутствует. Свежие backup
  непосредственно до/после совпали по всем полям, кроме createdAt; изображение цели
  также совпало. Между загрузкой и активацией OTA APK не переустанавливалась.
- Ручные действия капель/reset доступны. Полная проверка значений/литров/сохранения
  выполнена unit/browser тестами; на release выполнены действия 4 → reset → 3.
- Отдельный debug AVD воспроизвёл cold switch старого web-кода → `.2` после очистки
  только HTTP-кеша ресурсов и включения airplane mode: root отрисован, статус success.
  localStorage/IndexedDB/история при этой диагностике не очищались. Исходный timeout
  этим повтором не воспроизвёлся. Это дополнительная диагностика, не замена signed теста.
- Реальный rollback `.1` → `.7` уже проверил защиту без потери данных. Дополнительный
  искусственный crash-пакет остался только локальным QA fixture и не публиковался.

Для снятия блокировки нужна диагностика первого bootstrap/ready timeout с сохранением
сигналов загрузки WebView, JS-ошибок, восстановления состояния и вызова readiness.
Причина должна быть установлена, исправление проверено signed cold-start тестом,
а защита rollback оставлена включённой. Просто увеличить timeout, пересобрать ZIP
или потребовать онлайн-запуск вместо установления причины недостаточно.

Локальное доказательство без ключей: `C:\Temp\moyritm64-apple-removal-proof.json`.
QA channel приостановлен прежним подписанным механизмом (`enabled=false`, без
release): новые загрузки прекращены, существующие ZIP не заменялись. Уже активная
`.2` не отозвана и остаётся локально доступна на синтетических AVD. Stable не затронут.

## Production gate и будущая Samsung-проверка

Stable manifest **не опубликован**, stable rollout не запускался, новая PWA на Pages
не публиковалась, main не объединялся. QA-канал Samsung не получает.
QA bundle и зафиксированные исходники сохранены для диагностики. Они ещё не имеют
полной stable QA-приёмки; manifest заранее не создаётся в обход readiness,
clean-main/acceptance gate. Сначала требуется снять описанную блокировку.

Только после отдельного разрешения пользователя:

1. Согласовать review/merge Android-ветки в main и разрешение stable OTA отдельно.
2. На чистом reviewed main повторить gate/tests/build. Android native code и схемы
   должны по-прежнему соответствовать APK 1.1.0 (3); иначе остановиться.
3. Упаковать новый уникальный stable id, например после проверки свободного имени:
   `node scripts/build-ota.mjs --channel=stable --version=1.1.1 --id=NEW-STABLE-ID --accepted=yes`.
4. Только после разрешения задать `MOYRITM_OTA_ACCEPTED=yes` и вызвать
   `node scripts/publish-ota.mjs ota-output/stable/NEW-STABLE-ID`.
   Скрипт сначала загрузит/проверит immutable ZIP, затем обновит stable manifest.
5. Пользователь сохраняет свежий backup, открывает «Здоровье → Настройки →
   Обновления приложения» и проверяет загрузку. После «Готово к следующему запуску»
   полностью закрывает приложение и открывает снова, без удаления или новой APK.
6. Проверить новую OTA-версию, отсутствие Apple Health, воду/историю/финансы/облако
   и offline. При неисправности остановить stable/revoke прежним подписанным механизмом,
   не очищая данные и не удаляя приложение. Offline-отзыв мгновенным не бывает.

HealthState/FinanceState/localStorage/IndexedDB schemas, backup, vault, attachments,
share, learning selector, таймеры и расчёты не менялись. Миграции нет. Пользовательские
данные, облачные копии и установленные на Samsung приложения не очищались/не менялись.
