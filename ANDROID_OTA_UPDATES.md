# Облачные обновления Android «Мой ритм»

## Статус задачи 64

Рабочая ветка `feat/android-ota-64` продолжает задачи 62 и 63, не старый main.
Подготовлена версия **1.1.0 / code 3**, package ID и ключ APK не меняются.
Подписанная сборка и отдельные тесты обновления 2 → 3 завершены:
**READY FOR SAMSUNG OTA TEST**, не физическая Samsung-приёмка.
Samsung и production stable не включались; PWA и её GitHub Pages не изменялись.
Результаты проверок фиксируются в `ANDROID_OTA_VERIFICATION.md`.

## Как это будет работать

Приложение сразу открывается из локальных файлов и показывает сохранённые данные.
После успешной загрузки существующих данных оно подтверждает `notifyAppReady()` и
проверяет канал в фоне. Новая web-версия скачивается, проверяется и ждёт следующего
полного запуска. Переход в другое приложение и возврат не перезагружают экран и
не сбрасывают ввод. Принудительной кнопки «Применить сейчас» нет.

Без интернета продолжает работать последняя локальная версия. Уже проверенный
и сохранённый пакет может активироваться при следующем запуске offline.
Проверка обновлений не требует аккаунта Capgo или платной подписки.

Сначала потребуется **одно обычное обновление APK**: установленная 1.0.0 (2)
ещё не содержит updater. Новая 1.1.0 (3) подписывается прежним постоянным ключом
и устанавливается **поверх**, без удаления приложения и восстановления истории.
Это не debug → release migration из задачи 63. Удалять приложение не нужно.
Перед ручной установкой всё равно сохраните свежий backup и ключ облака.
Samsung-установка выполняется пользователем отдельно, после технической проверки.

## Что обновляется по интернету

HTML, CSS, JavaScript и совместимые локальные ресурсы интерфейса. Нативные плагины,
Java/Kotlin, AndroidManifest, permissions, Gradle/SDK и подпись OTA не обновляет.
Для них нужен новый подписанный APK с большим versionCode.

Схемы финансов, здоровья, localStorage/IndexedDB и backup в задаче 64 не менялись.
Будущие изменения хранения требуют отдельной проверки и плана миграции.
Наличие rollback само по себе не гарантирует обратимость произвольной миграции.

## Где посмотреть версию

Android: **Здоровье → Настройки → Обновления приложения**.
Здесь показаны версия APK, активная OTA-версия, последняя успешная проверка,
состояние загрузки и кнопка «Проверить обновления». В PWA блока нет.
Service worker PWA не запускается в Android; интерфейс не загружается постоянно
с GitHub Pages и не зависит от него для открытия.

## Архитектура и защита

- `@capgo/capacitor-updater` **8.53.0**, совместимый с Capacitor **8**; MPL-2.0.
  Используется manual mode (`autoUpdate: false`), не POST auto-update API.
- Manifest/channel: статический подписанный JSON в отдельной ветке GitHub,
  `https://raw.githubusercontent.com/ddpdantes-pixel/salary-control/android-ota-qa/channel.json`
  либо `android-ota-stable/channel.json`. GitHub Pages production не перезаписывается.
  GitHub CDN может отдавать предыдущий указатель до нескольких минут; клиент не
  обещает мгновенного распространения. Ошибка сети/канала не блокирует приложение.
- Пакеты: отдельные GitHub Releases с тегами `android-ota-qa-*` / `android-ota-stable-*`.
  Новый пакет получает новый URL. Скрипты не заменяют ZIP/тег существующего выпуска.
  Даже при подмене файла на сервере криптографическая проверка должна отказать.
- Capgo V2: AES-128-CBC, RSA-2048 PKCS#1 session/checksum wrappers, SHA-256 ZIP.
  Public key закреплён в нативном APK; plain/неподписанный ZIP не принимается.
- Весь точный текст metadata дополнительно подписан **RSA-PSS/SHA-256**, salt 32.
  Проверяется нативным кодом до доверия URL, checksum, версии и совместимости.
- Metadata содержит package ID, канал, monotonic sequence, срок до 7 дней,
  OTA version, build ID, nativeMin/nativeMax по **versionCode**, contract fingerprint,
  SHA-256 ZIP и криптографические параметры Capgo V2. Совместимость не определяется
  одним versionName. Старый sequence, чужой канал/пакет и несовместимый APK отклоняются.
- Контракт native/storage закреплён в APK через `ota/native-baseline.json`.
  Упаковщик сравнивает исходные native-файлы, версии плагинов и защищённые файлы
  хранения с этой базой. Нативный verifier сравнивает fingerprint metadata с APK.
  Нельзя просто переписать baseline и отправить пакет старой APK: её pin не изменится.
  Этот консервативный gate не заменяет ручной review всех изменений и регрессию.
- Отключены Capgo Cloud endpoints, статистика, preview и shake menu. Updater хранит
  служебные данные отдельно от бизнес-состояния (native preferences и собственная
  запись `CapacitorUpdater.webViewSession`); существующие схемы приложения не меняются.
- В объединённом Android manifest появились обычные разрешения библиотек updater /
  WorkManager: WAKE_LOCK, ACCESS_NETWORK_STATE, RECEIVE_BOOT_COMPLETED,
  FOREGROUND_SERVICE и служебное DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION.
  Новых опасных runtime-разрешений (контакты, здоровье, геолокация и т.п.) нет.
- Проверяется свободное место. Неудачный build не скачивается по кругу автоматически;
  версия с упавшим bootstrap блокируется. Повторная ручная попытка сетевой загрузки
  доступна, но не отменяет проверку подписи и блокировку неисправного bootstrap.

## Rollback

`appReadyTimeout = 30000 ms`. Подтверждение даётся после Android-адаптеров,
существующего восстановления состояния и отрисовки экрана, не в начале main.tsx.
При ошибке bootstrap или отсутствии подтверждения Capgo возвращает последнюю
успешную версию либо встроенные assets. Предыдущая успешная версия сохраняется.
Данные приложения при этом не очищаются.

Новый пакет только ставится в собственную очередь. `CapacitorUpdater.next()`
не вызывается: его background-активация могла бы потерять незавершённый ввод.
Очередь берётся один раз до React mount нового Activity. При изменении native
versionCode старая очередь не активируется; Capgo также сбрасывает старые OTA
при обновлении нативной версии. Отзыв уже работающей версии применяется при
следующем безопасном запуске, а не посреди редактирования.

## Два разных ключа

**Android signing key** остаётся прежним: `C:\Users\User\AndroidKeys\MoyRitm\moyritm-release.jks`.
Он подписывает APK. Пароль вводится только локально через запускатель задачи 63.

**OTA private key** создан отдельно: `C:\Users\User\AndroidKeys\MoyRitmOTA\moyritm-ota.private.pem`.
Проверена совпадающая локальная копия в `C:\Users\User\AndroidKeys\MoyRitmOTA-backup\`.
Каталоги имеют ограниченный Windows ACL (текущий пользователь и SYSTEM). Сам PEM
не зашифрован паролем; ACL не защищает от администратора или вредоносного ПО.
Обе копии на одном ПК не заменяют независимую защищённую offline-копию.
Не отправляйте приватный файл в чат/Git. В Git находится только `ota/public-key.json`.
Не пересоздавайте ключ для следующего выпуска: старые APK доверяют старому public key.

## Сборка новой APK

После всех проверок пользователь запускает локально **одну** команду:

```powershell
& 'C:\Users\User\OneDrive\Документы\salary-control\scripts\build-android-release.cmd' -PrepareOtaTest
```

Пароль прежнего Android keystore вводится в открывшемся локальном терминале,
не в чате. Запускатель сначала создаёт отдельную подписанную QA APK, затем обычную
stable 1.1.0 (3). Проверяет подпись, native version, канал, public key и contract pin.
QA APK остаётся только для эмулятора, Samsung не получает QA автоматически.
В конце обычная APK: `android/app/build/outputs/apk/release/app-release.apk`.
Скрипт не устанавливает APK, не публикует OTA и не меняет устройство пользователя.

## Воспроизводимый выпуск web-пакета

До stable необходимы review, тесты, согласование и чистый `main`, содержащий Android.
В задаче 64 merge/push в main и production-выпуск не выполняются.

1. Проверить ветку, diff и совместимость. Изменения native/storage останавливают OTA.
2. Выполнить frontend, Worker, Android OTA tests, Oxlint и оба TypeScript.
3. Выполнить Android web build с base `/` и Capacitor sync (PWA build — отдельно).
4. Создать пакет с новым уникальным id/version. Пример QA:

```powershell
node scripts/build-ota.mjs --channel=qa --version=1.1.1-qa.NEXT --id=NEW-UNIQUE-ID
```

5. Упаковщик использует ZIP с `/`-разделителями, проверяет разрешённые web assets,
   считает SHA-256, шифрует/подписывает и сохраняет metadata. Ничего не публикует.
6. `node scripts/publish-ota.mjs ota-output/qa/NEW-UNIQUE-ID` создаёт новый QA release,
   загружает ZIP и повторно скачивает его по публичному HTTPS для проверки SHA-256.
7. **Только после успешной проверки файла** подписанный channel обновляется последним.
   Ошибка загрузки/проверки оставляет прежний указатель. Конкурентная запись защищена
   GitHub SHA; sequence должен увеличиваться. Секрет GitHub берётся из имеющегося
   credential manager только в память и не печатается.
8. Проверить фактическое скачивание/активацию на эмуляторе, данные и rollback.
9. После отдельной пользовательской приёмки повторить выпуск для stable. Для него
   дополнительно требуются `--accepted=yes`, `MOYRITM_OTA_ACCEPTED=yes`, чистый main
   и совпадающий commit упаковки/публикации. Эти флаги не заменяют приёмку.

Пакеты с `--fault=...` разрешены только в QA для негативных тестов. В stable они
запрещены. Артефакты `ota-output/`, APK и приватные ключи исключены из Git.
Baseline создаётся `node scripts/ota-compatibility.mjs --write-native-baseline`
только при подготовке нового проверенного APK, не как обход ошибки OTA gate.

## Остановка распространения и отзыв

```powershell
node scripts/update-ota-channel.mjs qa pause
node scripts/update-ota-channel.mjs qa revoke 1.1.1-qa.BAD
node scripts/update-ota-channel.mjs qa promote-existing ota-output/qa/KNOWN-GOOD-ID
```

`pause` останавливает новые загрузки. `revoke` также готовит возврат активной
отозванной версии к встроенной при следующем запуске. `promote-existing` повторно
проверяет уже размещённый файл и подписывает новый указатель с большим sequence;
старый ZIP не перезаписывается и не загружается повторно на сервер.
Для stable необходима отдельная приёмка и тот же защитный флаг.
Offline-устройство узнает об отзыве только после подключения к сети; абсолютного
мгновенного отзыва без интернета не обещаем. Срок channel до 7 дней требует
периодического перевыпуска подписанного указателя, но не повторной загрузки ZIP.

## Как проверить данные

На отдельном эмуляторе использовать только синтетический набор. Сравнить business
localStorage до/после (не служебную session-запись updater), IndexedDB изображения
цели, зарплату/продажи, финансы, здоровье и обучение. Проверить сохранённое облачное
подключение и restore, затем offline-запуск. Не очищать хранилища для «починки».
Не проводить автоматизированные тесты с настоящим cloud key пользователя.
