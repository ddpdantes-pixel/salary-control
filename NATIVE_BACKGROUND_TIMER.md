# Нативная растяжка — финальная APK и результаты проверки

База — принятый и опубликованный Aurora1.1.3/source6222396. Отдельная ветка codex/native-background-stretch. Native-кандидат1.2.0/code4; package ID и release certificate должны совпасть с1.1.0/code3. Публичные OTA-указатели в этом задании не меняются.

## Архитектура

Kotlin StretchClock — чистая state machine на elapsedRealtime. StretchController хранит один сеанс в отдельном SharedPreferences, включая revision/session ID, пройденные границы и monotonic anchor. WebView только читает состояние и посылает команды. На code3/PWA без capability остаётся прежний путь. Таймер лица остаётся прежним. HealthState, финансовые модели, схемы резервного копирования и галочки не меняются.

Новые сеансы:5/1/1/2/5, сигналы300/360/420/540/840секунд. Импорт v1/legacy сохраняет старые названия и порядок; сохранённый работающий JS-сеанс импортируется приостановленным, без фонового автозапуска. Пользователь явно продолжает его. Native является источником истины, JS-сигналы gym не запускаются одновременно.

## Android lifecycle, Doze и разрешения

Пользовательский Start из видимой Activity запускает mediaPlayback Foreground Service с обычным видимым уведомлением и управлением пауза/продолжить/stop. Resume из уведомления является явным пользовательским действием. Служба не запускается из BOOT_COMPLETED, не использует SHORT_SERVICE и прекращается на паузе/stop/завершении. Android17 требует foreground audio lifecycle/WIU: [официальная документация](https://developer.android.com/about/versions/17/changes/bg-audio).

Одного FGS/partial wake lock недостаточно: Doze игнорирует wake locks, а allow-while-idle alarms имеют девятиминутное ограничение. Поэтому для явно запущенного пользователем точного таймера применяется один ближайший AlarmClock с последовательным переносом на следующую границу. setAlarmClock будит устройство и работает в Doze: [API](https://developer.android.com/reference/android/app/AlarmManager#setAlarmClock(android.app.AlarmManager.AlarmClockInfo,%20android.app.PendingIntent)), [Doze](https://developer.android.com/training/monitoring-device-state/doze-standby).

Нативный таймер объявляет FOREGROUND_SERVICE, FOREGROUND_SERVICE_MEDIA_PLAYBACK, POST_NOTIFICATIONS, SCHEDULE_EXACT_ALARM, WAKE_LOCK и VIBRATE, помимо прежнего INTERNET. В объединённом APK также остаются прежние зависимости ACCESS_NETWORK_STATE, RECEIVE_BOOT_COMPLETED и DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION; они присутствовали уже в официальной1.1.0. Новый таймер BOOT_COMPLETED не слушает и из него не запускается. USE_EXACT_ALARM, battery-optimization exemption, микрофон, контакты, телефония и Bluetooth-доступы не запрашиваются. Для точного пользовательского действия Android допускает SCHEDULE_EXACT_ALARM с отзывным разрешением пользователя и более широким набором применений, чем USE_EXACT_ALARM: [permissions](https://developer.android.com/develop/background-work/services/alarms#exact-permission). Отказ не заменяется приблизительным таймером под видом надёжного; UI сообщает причину.

Отсчёт не зависит от системного времени. TIME_SET пересчитывает только RTC-время ближайшего AlarmClock/уведомления из monotonic остатка. Процесс после гибели/перезагрузки восстанавливает безопасную паузу и не запускает аудио скрыто. Force Stop не обещает невозможного продолжения. Запоздалые события пропускаются, никогда не ставятся в очередь. Граница коммитится до воспроизведения, финал не повторяется.

## Звук

Короткий PCM AudioTrack с USAGE_ALARM/CONTENT_TYPE_SONIFICATION, три импульса. Никаких requestAudioFocus, setStreamVolume, ducking, длинного голоса или silent keepalive. Ресурсы освобождаются после каждого сигнала; Stop отменяет текущий и будущие сигналы. Системный DND/громкость/маршрут/звонок могут влиять на слышимость. Фактическое микширование и Android17 hardening должны быть проверены, а не выведены только из вызова API.

## Проверенный переход между APK без удаления OTA

При проверке закреплённого @capgo/capacitor-updater8.53.0 найдено, что resetWhenUpdate=true удаляет все старые bundles при смене нативной версии независимо от autoDeletePrevious=false. Для новой APK этот параметр выключен. NativeOtaBootstrap перед созданием Bridge однократно выбирает builtin, сбрасывает только старые active/fallback/next pointers и несовместимую старую очередь. Маркер нативной версии фиксируется последним; ошибка сохранения останавливает запуск, следующий запуск повторяет переход. При обычном повторном запуске на том же versionCode совместимый активный/очередной OTA не затрагивается.

Файлы OTA, их success/error/pending records, sequence, revocations и пользовательские хранилища не очищаются. На API34 с синтетическими маркерами предыдущего code3 реально проверены три допустимых bundle ID, неизменность их файлов/records, переход на builtin и сохранение sequence/revocations. Это тест механизма в debug4; он не подменяет установку оригинальной release3 → release4. Первоначальная проба с недопустимым 11-символьным ID исключена из положительного результата: SDK принимает 10-символьные ID.

Native/storage fingerprint новой APK: `25a2a6c1b7e734f8280902c868728ad69e81046e77d57c3caf30a40d1d3b8e3d`. Старый code3 fingerprint и public stable1.1.3 не переписываются. Новый код отклоняет code3-only bundles через NATIVE_VERSION_NEWER и сообщает, что установлена новая версия, без предложения ненужной замены APK. Новая builtin содержит принятый Aurora и скраб для лица.

## Диагностика исходного ключа и отсутствие повторных запросов

Файл `C:\Users\User\AndroidKeys\MoyRitm\moyritm-release.jks` существует,3546байт; формат PKCS12; private-key alias `moyritm`. SHA256 файла: `F47AE62403AC5F94F2F26CDC2141F87BF3E7AC9EDAB75C55DEE11C2CC7CAFC75`. Файл не изменялся, новый release-ключ не создавался. Чтение метаданных с null password не проверяет MAC и не расшифровывает закрытый ключ; оно не объявляется успешным открытием.

Официальная APK1.1.0/code3 имеет сертификат SHA256 `C06C1844B6D30F5EB7015F2489EFE9000325096E4C4B98F722B8F8D6E1A549D2`. APK проверена apksigner. Соответствие сертификата внутри текущего PKCS12 подтверждено3ноября успешным открытием, MAC и private-key sign/verify challenge. Новый проверяющий инструмент закрепляет именно этот сертификат и не пропустит debug/посторонний ключ.

Точная причина исторического keytool exit1 не сохранилась: прежний Invoke-LocalCommand отбрасывал stdout/stderr и выдавал общий код ошибки. Он не доказывает неправильность пароля. Исправленная передача окружения проверена существующим SDK debug-keystore с его публичным тестовым паролем, без создания/подмены release-ключа. Проверка хранилища использует storepass; отдельный keypass нужен только для закрытого ключа. При однократном вводе единственного пользовательского пароля обеим операциям передаётся одно и то же буквальное значение, без изменения регистра, дефисов или обрезки пробелов.

VerifyReleaseKey.java теперь раздельно проверяет формат/alias, MAC и расшифровку store, совпадение оригинального сертификата, открытие private key и локальную подпись-проверку владения им. В отчёт выходят только разрешённые статусы, например KEYSTORE_INTEGRITY_OR_DECRYPTION_FAILED или STORE_OPENED_BUT_PRIVATE_KEY_UNLOCK_FAILED; пароль/закрытый ключ/сырой вывод инструментов не записываются. Неправильный сертификат и отсутствие credentials проверены отрицательными тестами.

Дополнительные keystore-копии не обнаружены в доступных OneDrive/Документах/рабочем столе/AndroidKeys, включая поиск игнорируемых файлов. Это не утверждение об отсутствии внешних резервных копий. До однократной проверки в стандартных project signing configs и process/user/machine environment сохранённых проверенных credentials не было. В прямых сообщениях текущего задания и явно приложенных ТЗ не найдено однозначного сохранённого значения пароля. Защищённый Read-Host старого процесса его не сохранял.

Обычные Windows-сборки через `android:release` и build-android-release.cmd теперь никогда не вызывают Read-Host. При наличии проверенного доступа они автоматически используют DPAPI Windows CurrentUser; при его отсутствии возвращают LOCAL_CREDENTIAL_NOT_ENROLLED без запроса пароля. Явный однократный вход — enable-local-signing.cmd. Он сохраняет доступ только после проверки оригинального сертификата и private key, затем собирает одну release APK. Целевой зашифрованный файл — `C:\Users\User\AndroidKeys\MoyRitm\moyritm-release.signing.dpapi.json`; реальный файл создан 3 ноября после успешной проверки ключа. Он находится вне Git и ограничен ACL текущего пользователя/SYSTEM. [Область защиты DPAPI CurrentUser](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dataprotectionscope?view=windowsdesktop-9.0).

DPAPI roundtrip проверен на несекретной тестовой строке: регистр/дефисы сохранены, открытого значения в файле нет, другой hash/alias отклоняется. Дополнительно 3 ноября отдельный процесс успешно повторно открыл исходный ключ из настоящего DPAPI-кэша без интерактивного ввода; сертификат и подпись challenge проверены. 3 ноября пользователь явно разрешил одну локальную проверку и сохранение доступа. Открыто ровно одно окно с -EnrollLocalCredential, без повторных запусков; состояние проверки фиксируется отдельно. Обычные сборки не открывают парольные окна.
